# API FinModel AI

Бэкенд: FastAPI, все роуты под префиксом `/api` (исключение — `/healthz`).
Формат: JSON. Аутентификация: подписанная кука `fm_uid` (itsdangerous, HttpOnly, SameSite=Lax, год).

---

## 1. Общие правила

**Аутентификация.** Все роуты, кроме `/healthz` и `POST /api/auth/login`, закрыты гардом
`require_user`: нет валидной куки → `401 {"detail": "Нужен вход"}`. Кука содержит
подписанный user_id — подделка невозможна без `SESSION_SECRET`. Сессия stateless:
сервер не хранит сессии, валидность = валидность подписи.

**Изоляция.** Каждый запрос оперирует только данными `user_id` из куки. Любая выборка
из БД имеет `WHERE user_id = ?`. Чужой id объекта → `404` (не `403`, чтобы не
раскрывать факт существования чужих объектов).

**Коды ошибок.**
| Код | Когда |
|---|---|
| 400 | пустое сообщение, неизвестная модель, пустой файл |
| 401 | нет/битая сессия, неверный логин-пароль |
| 404 | объект не найден **или принадлежит другому юзеру** |
| 413 | файл > 25 МБ или превышена квота хранилища (200 МБ на юзера) |
| 429 | анти-брутфорс на логине |

**Анти-брутфорс логина.** Ключ = `IP + логин` (нижний регистр). Окно 5 минут:
5 неудач → блок 15 минут, ответ `429` с текстом «Повторите через N мин».
Успешный вход сбрасывает счётчик. Хранится в памяти процесса (одноразовый
инстанс — допустимо; при рестарте счётчики обнуляются).

**Идемпотентность.** Создание чата/загрузка файла не идемпотентны (каждый вызов —
новый объект). PATCH/DELETE идемпотентны по смыслу (повторный DELETE → 404).

## 2. Служебные

### `GET /healthz`
Без авторизации. Для мониторинга и бейджа фронта.
```json
{
  "ok": true,
  "models": [{"id": "kimi-k3", "title": "Kimi K3", "mock": false}],
  "default_model": "kimi-k3",
  "kimi": "live", "model": "kimi-k3"
}
```
`models[].mock: true` = у модели нет ключа, она отвечает заглушкой (dev-режим).
Поля `kimi`/`model` — legacy-совместимость со старым фронтом.

## 3. Аутентификация

### `POST /api/auth/login`
Тело: `{"username": "vlad", "password": "…"}`.
- `200` → `{"ok": true, "username": "vlad"}` + Set-Cookie `fm_uid`;
- `401` — неверная пара; `429` — блок по анти-брутфорсу.

Логика: логин ищется в `users`; пароль сверяется PBKDF2-HMAC-SHA256 (200 000 итераций,
соль на хеш). Регистрации нет — юзеры сидятся из `SEED_USERS` при старте
(только отсутствующие; существующие не перетираются).

### `POST /api/auth/logout`
Стирает куку. Всегда `200 {"ok": true}` — логаут без сессии не ошибка.

### `GET /api/auth/me`
`{"id": "…", "username": "vlad"}`. Фронт дёргает при загрузке страницы:
`401` → показать форму логина.

### `GET /api/usage`
Расход токенов текущего юзера.
```json
{
  "totals": {"requests": 3, "prompt": 800, "completion": 400, "total": 1200},
  "by_day": [{"day": "2026-08-17", "total": 1200, "requests": 3}],
  "by_model": [{"model": "MiniMax-M3", "requests": 1, "prompt": 392,
                "completion": 212, "total": 604}]
}
```
Источник — таблица `usage_events`, пишется после каждого ответа LLM из
`usage`-чанка стрима. Если провайдер usage не вернул — пишется грубая оценка
(символы/4) с флагом `estimated`, чтобы учёт не проваливался молча.

## 4. Модели

### `GET /api/models`
```json
{"models": [{"id": "kimi-k3", "title": "Kimi K3", "mock": false},
            {"id": "MiniMax-M3", "title": "MiniMax M3", "mock": false}],
 "default": "kimi-k3"}
```
Правило видимости: модель попадает в список, только если у неё есть API-ключ
(`MOONSHOT_API_KEY` / `MINIMAX_API_KEY`). В dev-режиме (`MOCK_KIMI=1`) видны все,
все с `mock: true`. Дефолт — первая живая модель.

Оба провайдера OpenAI-совместимые; различия инкапсулированы в шлюзе `kimi.py`:
- **kimi-k3**: не принимает `temperature` (только 1) — поле не шлём;
- **MiniMax-M3**: шлём `reasoning_split: true` — «мысли» прилетают в
  `reasoning_details`, в чат попадает только чистый ответ.

## 5. Диалоги

Правила сортировки списка: закреплённые сверху (`pinned DESC`), внутри — по
времени последнего сообщения (пустые — по созданию).

### `GET /api/chats`
`{"chats": [{"id", "title", "pinned", "model", "created_at", "last_at"}]}`.
`last_at` — unixtime последнего сообщения или `null`.

### `POST /api/chats`
Тело (необязательно): `{"model": "MiniMax-M3"}`. Без тела — дефолтная модель.
`400` на неизвестную модель. Ответ — созданный чат. Заголовок всегда
«Новый диалог» — переименовывается автоматически (см. ниже).

### `PATCH /api/chats/{id}`
Тело — любой набор из: `{"title": "…", "pinned": true, "model": "kimi-k3"}`.
Правила: пустой title отклоняется; model валидируется по реестру (`400`);
чужой/несуществующий чат → `404`.

### `DELETE /api/chats/{id}`
Удаляет диалог и **все его сообщения** (каскад в коде, не в FK).
Файлы юзера не трогает — они живут на уровне аккаунта, не диалога.

### `GET /api/chats/{id}/messages`
```json
{"id": "…", "title": "…", "model": "kimi-k3",
 "messages": [{"role": "user|assistant", "content": "…", "created_at": 1.7}]}
```
Полная история (до 200 сообщений, старые сверху) — для отрисовки при переключении.

### `POST /api/chats/{id}/messages` — отправка, SSE
Тело: `{"content": "текст", "file_ids": ["…"]}` (оба пустыми → `400`).

Поток `text/event-stream`, события:
```
data: {"type": "delta", "text": "…"}        ← токены ответа по мере генерации
data: {"type": "done", "usage": {...}}      ← финал: usage записан в БД
data: {"type": "error", "message": "…"}     ← ошибка LLM/транспорта
```

Внутренняя логика (порядок важен):
1. Проверка владения чатом (`404` чужому).
2. Сообщение юзера пишется в БД **до** вызова LLM — не потеряется даже при сбое стрима.
3. **Автотайтл**: если чат ещё называется «Новый диалог», title ← первые 48 символов сообщения.
4. Контекст для LLM: стабильный SYSTEM_PROMPT (префикс — под Context Caching Kimi,
   не редактировать без нужды) → системное с датой → тексты документов из кеша
   (до 15 000 симв. на документ) → последние 20 реплик истории.
5. Стрим от провайдера → наружу дельты; по завершении — сообщение ассистента в БД,
   `usage_events` (с указанием модели чата), событие `done`.

**Гонка на клиенте**: обрыв соединения (закрыл вкладку, переключил диалог, reload)
отменяет генератор до записи ответа/usage — ответ в историю не попадёт.
Поэтому фронт ждёт обновления счётчика токенов как сигнала «записано».

## 6. Файлы

Жизненный цикл: `upload → processing → ready|error → (delete) → trash 7 дней → физическое удаление`.

### `POST /api/files`
`multipart/form-data`, поле `file`. Лимиты: 25 МБ на файл, 200 МБ суммарно на юзера
(`413`). Сохранение атомарное (tmp → rename), фоновая задача парсинга.
Ответ: `{"id", "name", "size", "status": "processing"}`.

**Парсинг — локальный и детерминированный** (`docparse.py`), не зависит от LLM:
- `txt/md/log/json/csv/tsv` — как есть (JSON форматируется, CSV → «|»-таблица);
- `pdf` — pypdf, до 60 страниц; PDF-скан без текстового слоя → запасной путь
  через Kimi Files API (если есть ключ), иначе `error`;
- `xlsx/xlsm` — openpyxl, до 20 листов × 300 строк, значения (data_only).

Распарсенный текст кешируется на диске (`parsed_path`) — повторно файл не парсится
ни при каких сообщениях; в контекст LLM идёт до 15 000 символов кеша.

### `GET /api/files`
Список файлов юзера **без удалённых** (`deleted_at IS NULL`).

### `GET /api/files/{id}`
`{"id", "name", "size", "status": "processing|ready|error"}` — фронт опрашивает раз в 2 с.

### `DELETE /api/files/{id}`
**Мягкое удаление**: ставится `deleted_at`, файл остаётся на диске `TRASH_TTL_DAYS = 7`
дней. Ответ: `{"ok": true, "trash_ttl_days": 7}`. Физически стирает почасовой
cleaner (`cleanup.py`), заодно он вычищает анонимных юзеров старше 30 дней
(наследие ранней версии; при закрытой регистрации срабатывать не должен).

## 7. Что сюда НЕ входит (и почему)

- **Регистрация** — закрыта продуктово; юзеры через `SEED_USERS`.
- **Скачивание файлов** — файлы нужны как контекст LLM, а не как файлообменник;
  выходной артефакт (Excel-модель) появится в срезе «Modelling Agent» как `reports`.
- **Пагинация** — лимиты (200 сообщений, списки целиком) достаточны для двух юзеров;
  при росте — cursor-пагинация на `created_at`.
