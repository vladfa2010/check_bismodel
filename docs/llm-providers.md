# LLM-провайдеры: Kimi (Moonshot) и MiniMax

Всё общение с LLM идёт через одну точку — `KimiGateway` в `backend/kimi.py`
(имя историческое: появился до мультипровайдерности). Бизнес-логика снаружи,
здесь только транспорт. Документ фиксирует: контракт шлюза, различия
провайдеров, найденные грабли и процедуру добавления нового провайдера.

## 1. Контракт шлюза

```python
async def chat_stream(messages, json_mode=False, model=None):
    yield ("delta", текст)   # куски ответа, по мере поступления
    yield ("usage", dict)    # ровно один раз, в конце
```

Гарантии вызывающему коду:
- **`delta` содержит только контент** — мысли reasoning-моделей сюда не
  протекают (см. `reasoning_split` ниже).
- **`usage` придёт всегда** — если провайдер его не вернул, шлюз считает
  грубую оценку и помечает `estimated: True`.
- Исключение вместо usage = вызов не состоялся; частичные `delta` при этом
  могли уже уйти клиенту (стрим есть стрим).
- `json_mode=True` → `response_format: {"type": "json_object"}` — нужен
  срезу №2 (Extraction Agent). Работает на обоих провайдерах
  (OpenAI-совместимая часть API), но **валидность JSON всё равно проверять** —
  гарантируется формат, не схема.

Ретраи: до 3 попыток. 429 → ждём `Retry-After` (кап 30 с); транспортные
ошибки и таймауты → backoff 1/2/4 с. НЕ ретраим: 4xx (кроме 429) — это
ошибка запроса, повтор не поможет. Таймаут 300 с (стримы длинные), connect 30 с.

## 2. Реестр моделей

Живёт в `config.available_models()` — список dict:

```python
{"id": "kimi-k3", "title": "Kimi K3", "provider": "moonshot",
 "base_url": ..., "key": ..., "mock": False}
```

Правила видимости:
- Модель **видна юзеру, только если у неё есть ключ** (`*_API_KEY` в env)
  или включён `MOCK_KIMI=1` (тогда видны все, все — mock).
- `default_model()` — первая **живая** (не-mock); без ключей — первая mock.
- `/api/models` отдаёт наружу только `id/title/mock`. Ключи никогда не
  покидают бэкенд.

Сейчас в реестре:

| Модель | Провайдер | Base URL | Ключ | Роль |
|---|---|---|---|---|
| `kimi-k3` | moonshot | `https://api.moonshot.ai/v1` | `MOONSHOT_API_KEY` (`sk-…`) | основная |
| `MiniMax-M3` | minimax | `https://api.minimax.io/v1` | `MINIMAX_API_KEY` (`sk-cp-…`) | альтернатива, reasoning |

Оба API — OpenAI-совместимые (`POST /chat/completions`, SSE, формат чанков).
Различия — в разделе 3.

## 3. Quirks по провайдерам (найдено опытом)

### Moonshot Kimi K3

- **`temperature` НЕ передаём вообще.** K3 принимает только значение 1;
  любое другое (включая наш прежний 0.3) → 400 `invalid temperature`.
  Решение: поле отсутствует в payload — дефолт провайдера нас устраивает.
- `max_completion_tokens: 4096` (новое имя; старое `max_tokens` не
  используем).
- Usage в стриме: присылает при `stream_options.include_usage` — учёт точный.
- Файлы: `POST /v1/files` (purpose=`file-extract`) + `GET /v1/files/{id}/content`
  — умеет OCR сканов. В основном пайплайне НЕ используется (парсим локально,
  docs/data-model.md), только fallback для PDF без текстового слоя.
- Доступность из РФ: api.moonshot.ai отвечает (проверено с VDS в РФ).

### MiniMax M3

- Ключи формата `sk-cp-…` (platform.minimax.io). Ключи другого формата —
  401 на любом хосте; хостов два (`api.minimax.io` — международный,
  `api.minimaxi.com` — китайский), мы на международном.
- **Reasoning-модель:** без параметра мысли прилетают вперемешку с ответом.
  `reasoning_split: true` в payload → мысли уходят в отдельное поле
  `reasoning_details`, в `delta.content` остаётся чистый ответ. Шлюз ставит
  флаг автоматически для provider=minimax.
- Usage по `include_usage` — присылает; если нет (или оборвался стрим) —
  срабатывает оценка шлюза.
- temperature не передаём — дефолт адекватный, общий payload без температуры
  работает на обоих.

### Учёт токенов: точность

- Провайдерский usage — точный, пишется как есть.
- Оценка шлюза (нет usage в ответе): `символы / 4` — грубо, погрешность до
  ±30% на русском. Флаг `estimated: True` до фронта доходит, но в БД не
  сохраняется (см. И-10 в docs/data-model.md) — отчётность по моделям
  считает оценки наравне с точными. Для биллинга такое не годится, для
  внутренней аналитики — приемлемо.

## 4. Mock-режим

- `MOCK_KIMI=1` — принудительно все модели mock (разработка и e2e).
- Без `MOCK_KIMI`: mock только у моделей без ключа; модели с ключом — live.
- Mock-ответ детерминирован (фраза-маркер «Это ответ бэкенда в mock-режиме»),
  стримится пословно с задержкой 30 мс — e2e проверяет именно маркер,
  поэтому тесты не ходят в платные API.
- Mock-usage считается по-своему (символы/3, слова) — цифры правдоподобны,
  счётчик в UI растёт, сценарии учёта работают.

## 5. Как добавить провайдера (процедура)

1. Завести env: `<NAME>_API_KEY`, `<NAME>_BASE_URL`, `<NAME>_MODEL`
   (config.py, блок рядом с MiniMax).
2. Добавить запись в `available_models()` с уникальным `provider`.
3. Если API OpenAI-совместимый — шлюз работает без правок. Если есть
   особенности payload (как `reasoning_split`) — добавить ветку по
   `spec["provider"]` в `chat_stream`.
4. **Проверить quirks вручную до включения:** temperature, имя поля лимита
   (`max_tokens` vs `max_completion_tokens`), usage в стриме, поведение при
   429. Результаты — дописать в раздел 3 этой страницы.
5. Пробросить env в `deploy/docker-compose.yml` (контейнер видит только
   перечисленное — история бага: MINIMAX_* забыли, модель молча пропала).
6. E2E: сценарий 9 проверяет селектор моделей; новая модель в mock-режиме
   появится автоматически — поправить ожидание «две модели» → три.

## 6. Выбор модели под задачу (наблюдения)

| Задача | Рекомендация | Почему |
|---|---|---|
| Диалог о бизнес-модели | любая, по вкусу юзера | качество сопоставимо, разница в стиле |
| Extraction (JSON) | решить на эталонных сценариях среза №2 | важна дисциплина схемы, не красота текста |
| Длинные документы | Kimi | у Moonshot сильнее файловый стек |

Решение про extraction зафиксировать в docs/roadmap.md (срез 2, открытые
вопросы) после сравнения — не по впечатлению, а по валидации схемы на
трёх сценариях.
