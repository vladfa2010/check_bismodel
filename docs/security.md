# Политика безопасности FinModel AI

Как устроена защита: аутентификация, сессии, изоляция, секреты, файлы, сервер.
В конце — честный список известных ограничений: то, что мы знаем и осознанно
приняли (или планируем чинить), а не то, что «так получилось».

## 1. Принципы

1. **Секретов в коде и документации нет.** В репо — только имена переменных
   (`MOONSHOT_API_KEY`), форматы (`sk-cp-…`) и плейсхолдеры. Значения живут в env
   и в `deploy/.env` на сервере (`chmod 600`, в git не коммитится).
2. **Чужие данные недостижимы по построению, а не по надежде.** Каждый запрос
   к данным фильтруется по `user_id` из сессии; нарушение владения отвечает 404.
3. **Минимум движущихся частей.** PBKDF2 и подписанные куки — на stdlib +
   itsdangerous, без самописной криптографии и лишних зависимостей.
4. **Отказ = закрыто.** Парсинг файла не удался → статус «ошибка», а не отправка
   сырого бинарника в LLM; нет ключа модели → mock-режим, а не падение.
5. **Ограничения документируем честно** (раздел 10), а не делаем вид, что их нет.

## 2. Аутентификация

- **Регистрация закрыта продуктово.** Пользователи создаются только через
  `SEED_USERS` (env при старте, JSON `{"login": "password"}`). Существующие
  юзеры при рестарте не перетираются — смена пароля = правка хеша в БД вручную.
- **Хранение паролей:** PBKDF2-HMAC-SHA256, 200 000 итераций, случайная соль
  16 байт на пользователя. Формат записи: `pbkdf2$<iters>$<salt_hex>$<digest_hex>`.
  Пароль в открытом виде нигде не хранится и не логируется.
- **Проверка пароля:** полный пересчёт digest + сравнение через
  `hmac.compare_digest` (constant-time, защита от timing-атак). Ошибка разбора
  записи = отказ, а не исключение наружу.
- **Сообщение об ошибке одинаковое** для «нет такого юзера» и «неверный пароль»
  («Неверный логин или пароль») — нельзя перебором узнать, какие логины существуют.

## 3. Сессии

- **Stateless:** сервер ничего не хранит. Кука `fm_uid` — itsdangerous
  `URLSafeSerializer` (HMAC-SHA1-подпись itsdangerous поверх payload),
  внутри только `user_id`. Подделка невозможна без `SESSION_SECRET`.
- **Флаги куки:** `HttpOnly` (JS не читает), `SameSite=Lax` (CSRF на POST
  затруднён: кросс-сайтовые POST куку не несут), `max_age` 1 год.
- **Следствие stateless — см. ограничение в разделе 10:** отозвать конкретную
  сессию нельзя, только разлогинить всех сменой `SESSION_SECRET`.

## 4. Анти-брутфорс (логин)

- Ключ счётчика: `IP | username` (нижний регистр) — лочится пара, а не весь IP
  и не юзер целиком (нельзя залочить чужой аккаунт с другого адреса).
- Правило: **5 неудач за 5 минут → блокировка на 15 минут**, ответ 429
  с текстом «Слишком много попыток. Повторите через N мин.». Окно скользящее:
  при каждой попытке выбрасываются фейлы старше `окно + блок`.
- Успешный логин обнуляет счётчик пары.
- Хранение — в памяти процесса (см. ограничение: сброс при рестарте).
- Проверено e2e-сценарием 6: 429 приходит, текст про минуты есть.

## 5. Авторизация и изоляция данных

- **Модель доступа:** всё принадлежит `user_id` — диалоги, сообщения, файлы,
  usage. Каждый SELECT/UPDATE/DELETE содержит `WHERE user_id = ?`.
- **404 вместо 403.** Запрос к чужому диалогу/файлу возвращает «не найдено» —
  сам факт существования чужого объекта не раскрывается.
- **Изоляция проверена e2e** (сценарий 5): victor не видит диалоги vlad,
  `/api/usage` показывает только свои токены.
- **Файлы на диске:** лежат в `DATA_DIR/files/<user_id>/…` — разнесены
  по каталогам владельца; имя на диске — uuid, оригинальное имя только в БД.

## 6. XSS и рендеринг

Правило: **любая пользовательская строка в DOM — только через `escapeHtml`
или `textContent`.** Экранируются: текст сообщений, ответы LLM (стрим — через
`textContent`), заголовки диалогов (в т.ч. из `prompt()` переименования),
имена и расширения файлов в чипах и в сообщении, тексты ошибок из API.
Статичная вёрстка (иконки, меню) вставляется как HTML без интерполяции.

Историческая находка при аудите: имя файла в чипах шло без экранирования
(self-XSS через имя загружаемого файла) — исправлено, правило выше покрывает
все новые места рендеринга.

## 7. Управление секретами

| Секрет | Где живёт | Кто видит | Ротация |
|---|---|---|---|
| `MOONSHOT_API_KEY` | env / `deploy/.env` | сервер | на platform.moonshot.ai |
| `MINIMAX_API_KEY` | env / `deploy/.env` | сервер | на platform.minimax.io |
| `SESSION_SECRET` | env / `deploy/.env` (`openssl rand -hex 32`) | сервер | смена = разлогин всех |

`deploy/.env` существует **только на сервере** — его не синхронизируют и не
бэкапят в репо; rsync-деплой идёт по whitelist-путям (см. docs/deploy.md).
| `SEED_USERS` (пароли) | env / `deploy/.env`, далее PBKDF2-хеши в БД | сервер | правка хеша в БД |
| root-пароль VDS | вне репо | владелец | `passwd` на сервере |
| GitHub PAT | вне репо | владелец | перевыпуск на github.com |

Правила:
- `.env` и `deploy/.env` в `.gitignore`; в репо только `.env.example` с плейсхолдерами.
- Секреты в выводе команд и логах маскируются (`sed 's/sk-…/***/'`) при работе через SSH.
- Тестовые пароли — тоже не в коде: e2e берёт пароль из `E2E_PASSWORD`
  (см. docs/tests.md, правило 5).
- Ключ LLM никогда не уходит на фронт: `/api/models` отдаёт только
  id/название/mock-флаг, вызовы LLM идут только с бэкенда.

## 8. Файлы и данные

- **Лимиты:** 25 МБ на файл; PDF — до 60 страниц, XLSX — до 20 листов × 300 строк.
- **Парсинг локальный** (docparse): txt/md/csv/json, PDF через pypdf, XLSX через
  openpyxl. В LLM уходит **только извлечённый текст** в контексте диалога —
  сам файл провайдеру не передаётся (исключение: fallback на Kimi Files API
  для PDF-сканов без текстового слоя, только если не mock-режим).
- **Soft delete:** удалённый файл помечается `deleted_at`, физически стирается
  через 7 дней фоновой задачей. До стирания — восстановим из «корзины».
- **Удаление диалога** стирает его сообщения и отправляет в корзину файлы,
  прикреплённые к этому диалогу (7 дней до физического стирания).
- **SQLite в WAL**, один писатель через asyncio.Lock — гонок записи нет.

## 9. Транспорт и сервер

- **TLS:** Caddy с автоматическим сертификатом Let's Encrypt на домен
  `46.173.27.26.sslip.io`. Голый IP отвечает по HTTP без редиректа на HTTPS-IP
  (чтобы не было ошибки сертификата) — рабочая точка входа только домен.
- **Заголовки (Caddy):** `Cache-Control: no-cache` для HTML (после деплоя юзер
  не получает старый JS), плюс стандартный security-набор в блоке `header`.
- **Сеть:** ufw — открыты только 22/80/443; fail2ban на SSH.
- **Контейнер:** приложение в Docker, данные в именованном volume
  (`appdata` → `/var/data`), образ без секретов (всё через env).
- **SSE:** `flush_interval -1` у Caddy — стрим не буферизуется; при этом
  тело ответа не логируется.

## 10. Известные ограничения (честно)

1. **Сессии не отзываются точечно.** Stateless-подпись: «выкинуть» одного юзера
   можно только сменой `SESSION_SECRET` — разлогинит всех. Принято: юзеров двое,
   риск ок. Roadmap: серверные сессии с `expires`/`revoked`.
2. **Анти-брутфорс в памяти.** Рестарт backend обнуляет счётчики; защита не
   распределённая (у нас один процесс — ок). Атакующий с фермой IP снимет
   per-IP-часть, но ключ включает username — объём перебора не растёт.
3. **Нет rate-limit на чат и загрузку файлов.** Авторизованный юзер может
   жечь токены LLM без ограничений. Принято (юзеры доверенные), roadmap —
   дневная квота по usage.
4. **Нет бэкапов.** БД и файлы на одном VDS, снапшоты Beget — вручную.
   Roadmap: litestream/cron-дампы.
5. **Секреты проходили через чат-переписку** (root-пароль, оба LLM-ключа) —
   рекомендована ротация: `passwd` на сервере + перевыпуск ключей на платформах.
   После ротации обновить `deploy/.env` и перезапустить compose.
6. **Пароль seed-юзеров был в git дважды: в `tests/e2e_test.py` и как дефолт
   `SEED_USERS` в `backend/config.py`** — и это боевой пароль прода (в prod-`.env`
   `SEED_USERS` не задан, юзеры сидятся дефолтом). При аудите: из тестов пароль
   вынесен в `E2E_PASSWORD`, дефолт в config.py заменён на `dev-only-change-me`.
   **Git-история скомпрометирована → пароли vlad/victor на проде сменить
   обязательно** (пересидирование: удалить юзеров из БД + задать `SEED_USERS`
   в `deploy/.env` + recreate, либо правка хешей в БД напрямую).
7. **Логирование без аудита.** Кто когда логинился/удалял — не пишется.
   Roadmap: таблица audit_log.

## 11. Инцидент: что делать

1. Подозрение на утечку `SESSION_SECRET` → сменить значение в `deploy/.env`,
   `docker compose up -d` — все сессии мертвы.
2. Утечка LLM-ключа → отозвать на платформе провайдера, выписать новый,
   обновить `.env`, перезапуск.
3. Компрометация юзера → убрать/сменить запись в БД (хеш), сменить
   `SESSION_SECRET`, проверить `usage` на аномалии.
4. Компрометация сервера → считать скомпрометированными всё: `.env`, БД,
   файлы юзеров. Переустановка, ротация всех секретов из таблицы раздела 7.
