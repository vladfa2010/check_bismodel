# Фронтенд: архитектура static/index.html

Один файл, ~775 строк: разметка + Tailwind (CDN) + vanilla JS без сборки.
Это осознанное решение: фронт — тонкий клиент над API, а не SPA с состоянием.
Когда файл перестанет помещаться в голове за одно чтение — пора резать на
модули; до тех пор карта этого файла живёт здесь.

## 1. Карта файла (сверху вниз)

| Строки | Блок | Содержимое |
|---|---|---|
| 1–250 | Разметка | сайдбар (юзер, usage, модели, история), логин-оверлей, чат, empty state, drop-зона |
| 250–365 | Файлы | `pendingFiles`, загрузка, поллинг статуса, чипы, drag&drop |
| 365–425 | Рендер сообщений | пузыри, typing-индикатор, `escapeHtml` |
| 426–505 | Отправка и SSE | `sendMessage` → `sendReal`: fetch + ReadableStream |
| 505–560 | Auth | логин/логаут/`loadMe`, текущий юзер |
| 560–625 | Usage и модели | счётчики токенов (в т.ч. by_model), селектор модели |
| 625–735 | Диалоги | список, меню «⋯», создание, переключение |
| 734–774 | Инициализация | `detectBackend`, suggest-кнопки, старт |

## 2. Глобальное состояние (всё — плоские переменные)

```javascript
pendingFiles = []    // {id, name, size, ext, file, status, serverId} — чипы до отправки
busy = false         // идёт стрим/запрос — sendMessage молча игнорирует повтор
realMode = false     // бэкенд отвечает на /healthz
currentUser = null   // из /api/me
currentChatId = null // активный диалог; null = «ещё не создан»
streamAbort = null   // AbortController активного стрима
modelsList = []      // /api/models
chatsCache = []      // последний ответ /api/chats (для меню и переключения)
```

Правила:
- **Источник правды — сервер.** Кеши (`chatsCache`, `modelsList`) только для
  рендера; любое действие идёт в API, потом перезагрузка кеша.
- `currentChatId` может быть `null` — диалог создаётся не кнопкой «+»,
  а первым сообщением (ленивое создание на сервере, см. docs/api.md).
  Кнопка «Новый диалог» делает POST /chats явно — чтобы пустой диалог сразу
  был в истории.

## 3. SSE-клиент (самое хрупкое место)

`sendReal` читает ответ через `fetch` + `resp.body.getReader()`
(не EventSource — нам нужен POST с JSON):

```
buf += decoder.decode(value, {stream: true})   // потоковое декодирование UTF-8
events = buf.split('\n\n'); buf = events.pop() // хвост — недошедшее событие
каждое событие: 'data: {json}' → delta | error
```

Протокол — в docs/api.md. Правила на клиенте:
- **Текст стрима пишется через `textContent`** (`bubble.textContent = acc`),
  никогда через innerHTML — ответ LLM не экранируется постфактум.
- Ошибка протокола (`type: error`) рендерится в тот же пузырь красным,
  через `escapeHtml`.
- Пустой стрим (ни одной delta) → «…» — не молчим.
- После завершения: `loadChats(true)` (автотайтл в сайдбаре) и `loadUsage()`.
- `401` посреди отправки → оверлей логина, ввод не теряется логически
  (сообщение уже в БД на сервере — оно появится после повторного входа).

**Переключение диалога во время стрима:** `openChat`/`newChat` делают
`streamAbort.abort()`. `AbortError` глотается (`e.name !== 'AbortError'`) —
это не ошибка, а штатная отмена. Гонка «старый стрим дописался в новый
диалог» невозможна: запрос помер на клиенте, а сервер привязывает ответ
к chat_id из URL, не к UI.

## 4. Рендер и XSS

Правило из docs/security.md: пользовательская строка → `escapeHtml()` в
HTML-шаблоне либо `textContent`. Применяется к: тексту сообщений, ответам
LLM, заголовкам диалогов (включая `prompt()` переименования), именам и
расширениям файлов, сообщениям об ошибках от API. Статика (SVG-иконки,
каркасы) интерполяции не содержит.

Исторический баг (зафиксирован в security.md): имя файла в чипах шло без
экранирования. При добавлении нового рендера — мысленный чек: «откуда эта
строка?» Если от юзера/сервера — экранировать.

## 5. Файловый конвейер

```
addFiles (input/drag&drop) → чип status:'local'
  → uploadToServer (POST /api/files, FormData) → status:'processing', serverId
  → pollFileStatus (GET /api/files/{id} раз в 2 с, до 60 раз) → ready | error
sendMessage берёт files с serverId — незагруженные просто не прикрепляются
```

- Лимит 25 МБ проверяется и на клиенте (быстрый отказ), и на сервере
  (истинный).
- Drag&drop: счётчик `dragDepth` вместо флага — `dragleave` дочерних
  элементов не гасит оверлей раньше времени.
- `removeFile` до отправки — только из чипов (на сервере файл при этом
  уже может существовать; он подчистится корзиной/квотой — осознанно
  не делаем DELETE на каждый чих).

## 6. Режимы: real / mock / демо

`detectBackend` при загрузке дергает `/healthz`:
- отвечает → `realMode = true`; бейдж показывает живые модели
  (`h.models` без `mock`) или «LLM mock (нет ключей)»;
- не отвечает → демо-режим (фолбэк Render-статики): бейдж «демо»,
  `sendMessage` вместо сети показывает «Сервер недоступен».

Один и тот же HTML умеет быть и продом, и статическим прототипом —
поэтому демо-ветка не удаляется.

## 7. Правила для правок фронта

1. **Новый рендер пользовательских данных — только через escapeHtml/
   textContent** (раздел 4).
2. **Новый fetch с телом — с `signal: streamAbort.signal`**, если его имеет
   смысл отменять при переключении диалога.
3. **Никаких `setTimeout`-синхронизаций** с сервером: ждём события
   (конец стрима, смена статуса файла, обновление счётчика usage). Это же
   правило тестов — docs/tests.md.
4. **Классы Tailwind важны для e2e**: селекторы тестов смотрят на
   `#historyList .chat-open`, `.streamText`, `#modelSelect` и т.п. —
   переименование класса = правка теста, это нормально, но осознанно.
5. Кеш браузера: HTML отдаётся с `Cache-Control: no-cache` (Caddy), поэтому
   деплой подхватывается обычным refresh. Если юзер «не видит фичу» —
   сначала жёсткая перезагрузка, потом расследование.
