# Промпты FinModel AI

Промпты — часть продукта и core IP: от них зависит, насколько цифрам в модели
можно доверять. Здесь: действующие промпты (дословно), правила их изменения,
как тестировать правки. Промпт в коде без записи здесь — баг документации.

## 1. Действующий: CHAT-SYSTEM v1

Живёт в `backend/routes_chat.py`, константа `SYSTEM_PROMPT`. Дословно:

> Ты — FinModel AI, ассистент для построения финансовых моделей бизнеса.
> Твоя задача — обсудить с пользователем его бизнес-модель: выручку, цены,
> клиентов, затраты, налоги, горизонт планирования. Задавай уточняющие вопросы
> по одному-два за раз, коротко и по делу. Отвечай по-русски.
> Никогда не выдумывай данные: если параметр неизвестен — спроси или явно пометь
> его как допущение. Если пользователь прислал документы — опирайся на них и
> указывай, из какого документа взята цифра. Финансовые расчёты не выполняй
> в уме: модель строит отдельный детерминированный движок.

**Логика каждого предложения:**

| Предложение | Зачем |
|---|---|
| «Ты — FinModel AI, ассистент для…» | Рамка роли: не универсальный чат, а интервьюер по бизнес-модели |
| «выручку, цены, клиентов, затраты, налоги, горизонт» | Чек-лист тем — без него модель уходит в абстрактные советы |
| «уточняющие вопросы по одному-два за раз» | Защита от «анкеты на 20 вопросов» — юзер бросает такие диалоги |
| «Отвечай по-русски» | Без явной инструкции модели съезжают на английский на финансовых терминах |
| «Никогда не выдумывай данные… спроси или пометь как допущение» | **Главное правило продукта.** Выдуманная цифра в модели убивает доверие навсегда |
| «опирайся на документы и указывай, из какого взята цифра» | Проверяемость: юзер может сверить источник |
| «расчёты не выполняй в уме… детерминированный движок» | LLM считает плохо; все вычисления — в срезе №3 (openpyxl-генератор). Запрещаем заранее |

## 2. Сборка контекста (порядок сообщений)

```
1. system: SYSTEM_PROMPT                 ← стабильный префикс, НЕ менять
2. system: "Текущая дата: YYYY-MM-DD"    ← переменная часть, после префикса
3. system: "Документ «name»:\n<текст>"   ← по одному сообщению на документ
4. user/assistant: история диалога       ← последние HISTORY_LIMIT (20) сообщений
```

**Правило стабильного префикса:** байт-в-байт одинаковое начало массива
messages попадает в Context Caching Kimi — дешевле и быстрее. Поэтому:
- `SYSTEM_PROMPT` меняем только осознанно (правка = сброс кеша у всех);
- всё переменное (дата, документы) — **после** префикса, никогда внутри него;
- документы — отдельными system-сообщениями, а не склейкой: границы документов
  видны модели, и добавление/удаление файла инвалидирует только хвост кеша.
- Текст документа режется по `DOC_TEXT_LIMIT` — файл не может вытеснить
  историю диалога из контекста.

## 3. Правила изменения промптов

1. **Одна правка = одна гипотеза.** «Поменял три фразы и стало лучше» —
   невоспроизводимо. Меняем одно, проверяем, фиксируем.
2. **Версия в комментарии коммита.** Формат: `CHAT-SYSTEM v2: +запрет
   финансовых советов (причина: …)`. Версии нумеруются здесь, в коде —
   только текущая.
3. **Регрессия важнее улучшения.** Перед мёржем промпт гоняется на эталонных
   сценариях (раздел 4): новое поведение не должно ломать старое.
4. **Никаких данных юзеров в промпте.** Промпт — константа; данные идут
   в сообщениях. Персонализация через промпт убивает кеш и усложняет отладку.
5. **Промпт не лечит то, что лечится кодом.** Если модель ошибается в формате —
   сначала думаем про валидацию/парсинг на нашей стороне, потом про промпт.

## 4. Эталонные сценарии (тестовый набор)

Три сценария, общие для промптов и extraction (docs/roadmap.md, срез 2):

| # | Сценарий | Что проверяет |
|---|---|---|
| Э1 | SaaS-подписка: 25 клиентов/мес, ARPU 12 000 ₽, churn 4% | минимальный набор допущений, рекуррентная выручка |
| Э2 | Кофейня у метро: средний чек, трафик, аренда, ФОТ | офлайн-юнит-экономика, сезонность |
| Э3 | Маркетплейс-продавец: комиссия площадки, выкуп, логистика | сложная структура расходов |

Проверка чат-промпта на сценарии: модель (а) задаёт вопросы по одному,
(б) не выдумывает недостающее, (в) ссылается на документ, если он приложен,
(г) не считает «в уме» итоговые цифры. Прогон — ручной, на живом ключе;
результат — короткая запись в коммит промпта (что прошло/не прошло).

## 5. Будущее: EXTRACTION-SYSTEM (срез №2, черновик требований)

Промпт Extraction Agent появится вместе со срезом №2; требования фиксируем
сейчас, чтобы не проектировать «в моменте»:

- **Вход:** история диалога + тексты документов (та же сборка контекста).
- **Выход:** строго JSON (`json_mode=True`, см. docs/llm-providers.md) по
  схеме: массив допущений `{key, label, value, unit, period, source,
  confidence}`, где `source` = `dialog | file:<имя> | default`,
  `confidence` = `high | low` (low → подсветить на экране проверки).
- **Запрет выдумывания действует и здесь:** параметр, не названный юзером,
  идёт со `source: default` и `confidence: low` — никаких «типичных значений»,
  выданных за факт.
- **Валидация кодом, не промптом:** парсим JSON, проверяем схему,
  невалидный → одна повторная попытка с текстом ошибки валидации → понятное
  сообщение юзеру. Промпт усиливает, но не заменяет проверку.
- Схема JSON при реализации среза №2 документируется здесь же, дословно.
