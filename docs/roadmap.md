# Roadmap FinModel AI

Продуктовая карта: что уже стоит, что дальше, и по каким критериям срез
считается готовым. Формат — срезы (вертикальные куски ценности, каждый
деплоится и тестируется отдельно), а не слои (сначала весь бэк, потом весь
фронт). Документ живой: статус обновляем по факту, а не по плану.

## Продукт в одном абзаце

Пользователь в диалоге с ИИ описывает свою бизнес-модель, прикладывает файлы
(выгрузки, заметки, Excel). Система извлекает из этого структурированные
допущения (выручка, расходы, темпы роста…), показывает их человеку на
проверку и собирает по ним живую Excel-модель с формулами. Ценность — не чат,
а **файл модели, которому можно доверять**, потому что человек проверил
допущения до расчёта.

## Срез 0 — прототип ✅

**Цель:** показать продукт, не написав ни строчки бэкенда.
GPT-подобный чат, аттачи, анимированный фон, генерация демо-xlsx на клиенте.

**Критерии готовности (выполнены):** выглядит как продукт; демо-сценарий
проходится без бэкенда; выложен на Render.

## Срез 1 — живой бэкенд ✅

**Цель:** заменить демо-логику настоящей, не сломав UX прототипа.
FastAPI + SQLite + SSE-стрим от Kimi; файлы с локальным парсингом;
закрытая регистрация (vlad/victor); анти-брутфорс; деплой на Beget VDS
(Docker + Caddy + HTTPS).

**Критерии готовности (выполнены):** e2e-набор зелёный; реальный ответ LLM
стримится в UI; токены считаются; HTTPS работает; мок-данных нет.

## Срез 1.5 — мульти-диалоги и модели ✅

**Цель:** диалог как первоклассная сущность.
CRUD диалогов, закрепить/переименовать/удалить, модель на диалог,
usage в разрезе моделей.

**Критерии готовности (выполнены):** 24/24 e2e, включая переключение во
время стрима, меню «⋯», персистентность выбора модели после reload.

## Срез 2 — Extraction Agent ⬜ NEXT

**Цель:** из диалога и файлов получить структурированные допущения, которые
человек может проверить глазами. **Это trust-critical срез**: если юзер не
поверит допущениям, модель он не откроет.

**Функционал:**
- Кнопка «Собрать допущения» в диалоге (не автоматом — юзер решает, когда
  контекста достаточно).
- LLM (JSON Mode) получает: историю диалога + извлечённые тексты файлов →
  возвращает JSON по схеме допущений (см. docs/prompts.md, схема EXTRACTION).
- Экран проверки: таблица допущений (название, значение, единица, источник —
  «из диалога» / «из файла X» / «по умолчанию»), редактирование вручную,
  кнопка «Утвердить».
- `chats.status`: `dialog → extracting → review`; результат в
  `chats.extraction_json`.
- Usage пишется с `kind='extract'` — увидим, сколько стоит извлечение.

**Критерии готовности:**
1. На трёх эталонных сценариях (SaaS-подписка, кофейня, маркетплейс) JSON
   валиден по схеме и покрывает ≥90% допущений, названных юзером в диалоге.
2. Каждое допущение имеет источник; значения «по умолчанию» визуально
   отличаются от названных юзером.
3. Ручная правка допущения сохраняется и попадёт в модель (проверяется в №3).
4. Ошибка JSON (LLM вернул мусор) — понятное сообщение и повтор, а не 500.
5. E2E: диалог → extract → правка → утверждение → статус review.

**Открытые вопросы:** выбор модели для извлечения (K3 vs M3 — сравнить на
этих же сценариях, решение зафиксировать здесь); один JSON на весь бизнес
или по разделам.

## Срез 3 — Сборка Excel-модели ⬜

**Цель:** из утверждённого `extraction_json` — xlsx с формулами, а не
зашитыми числами.

**Функционал:** задача сборки (`jobs` + SSE-прогресс), генератор на openpyxl
(выручка/расходы/прибыль по месяцам, 3 года), QA-проход (баланс сходится,
формулы не #REF, unit-экономика посчитана) → `reports.qa_json`, кнопка
«Скачать модель». `chats.status: review → building → done`, usage kind='build'.

**Критерии готовности:**
1. Файл открывается в Excel и LibreOffice без предупреждений.
2. Все расчётные ячейки — формулы; допущения вынесены на отдельный лист
   и адресуются по имени.
3. QA-проход зелёный на трёх эталонных сценариях; при красном — юзер видит
   причину, а не просто «ошибка».
4. E2E: от утверждённых допущений до скачанного файла.

**Открытые вопросы:** шаблон модели — фиксированный (быстрее, предсказуемее)
или генерируемый LLM (гибче, опаснее). Склоняемся к фиксированному каркасу
с LLM-заполнением.

## Срез 4 — Итерации ⬜

**Цель:** «а если churn будет 6%?» в диалоге → правка допущения → пересборка
за минуту. Diff-вью изменений между версиями модели; история версий
(копии `extraction_json` с метками времени).

**Критерий готовности:** юзер меняет одно допущение словами в чате и
получает новый файл, не открывая экран проверки заново (но с показом diff).

## Срез 5 — Коммерческая обвязка ⬜

Открытая регистрация (или инвайты), дневные квоты по токенам (usage уже

юзера. Почта/уведомления.

## Принципы дорожной карты

1. **Каждый срез деплоится и покрывается e2e до старта следующего.**
   Нет «почти готово» — есть статус и критерии.
2. **Trust before features.** Срезы 2–3 важнее любых удобств: продукт
   продаёт доверие к цифрам.
3. **Модель — сменная деталь.** Выбор LLM — инженерное решение (качество
   JSON, цена, скорость), не продуктовое; интерфейс провайдеров это
   гарантирует (docs/llm-providers.md).
4. **Не строим то, что просили один раз.** Запросы vlad/victor чинятся как
   баги, но фичей без подтверждённой потребности в roadmap не добавляем.
