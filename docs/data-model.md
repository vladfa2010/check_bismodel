# Модель данных FinModel AI

SQLite в WAL-режиме, один файл `DATA_DIR/app.db`, доступ только через
`backend/db.py`. Этот документ — единственное место, где схема описана целиком:
таблицы, инварианты, индексы, политика миграций и retention. При добавлении
таблицы/колонки сначала обновляется этот файл, потом пишется код.

## 1. Движок и конкурентность

- **Одно соединение** на процесс (`aiosqlite`, `row_factory=Row`), живёт всё
  время работы приложения; закрывается в `close_db()` при shutdown — иначе
  фоновый поток aiosqlite не даёт процессу завершиться.
- **`PRAGMA journal_mode=WAL`** — читатели не блокируют писателя.
- **`asyncio.Lock` на каждую операцию** (`_exec` и `_fetch`). SQLite всё равно
  один писатель, а лок делает порядок детерминированным: нет interleaving
  «прочитал-записал» между двумя корутинами. Производительности хватает:
  нагрузка — два пользователя.
- **Каждый `_exec` — отдельный commit.** Транзакций «несколько запросов
  атомарно» сейчас нет; где это важно (удаление диалога + сообщений),
  порядок запросов выбран так, чтобы частичное выполнение оставляло
  консистентное состояние (см. инвариант И-4).
- Все `id` — `uuid.uuid4().hex` (32 hex-символа, без дефисов).
- Все метки времени — `time.time()` (REAL, unix-секунды, UTC).

## 2. Схема (диаграмма связей)

```
users ──< chats ──< messages
  │  ╲────< files           (files.chat_id — привязка к диалогу, NULL = legacy)
  │  ╲────< usage_events ──> chats (chat_id, без FK)
  │
  └── username NULL = анонимный юзер (legacy, под авто-удаление)

chats ──< jobs      (зарезервировано под срез «сборка модели»)
chats ──< reports   (зарезервировано под срез «результат/QA»)
```

Внешних ключей (`FOREIGN KEY`) в DDL нет — целостность поддерживается кодом
(каскады в `delete_user_cascade`, `delete_chat`). Это осознанно: FK в SQLite
включались бы через `PRAGMA foreign_keys` на каждое соединение, а выгоды при
одном писателе минимальны.

## 3. Таблицы

### users — пользователи

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | uuid hex |
| `username` | TEXT, UNIQUE | логин; **NULL = анонимный юзер (legacy)** |
| `password_hash` | TEXT | `pbkdf2$iters$salt$digest`, см. docs/security.md |
| `created_at`, `last_seen_at` | REAL | last_seen обновляется при каждом запросе (`touch_user`) |
| `quota_bytes` | INTEGER | лимит диска юзера, default 200 МБ |

Инварианты:
- **И-1.** Регистрации нет: строки появляются только из `seed_users()`
  (идемпотентно — существующий username не перетирается, пароль при рестарте
  не меняется).
- **И-2.** `last_seen_at` — единственный сигнал активности; по нему же чистятся
  анонимные юзеры (см. retention).

### chats — диалоги

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | uuid hex |
| `user_id` | TEXT | владелец (все запросы фильтруют по нему) |
| `title` | TEXT | `'Новый диалог'` → автотайтл из 1-го сообщения |
| `pinned` | INTEGER | 0/1, закреплённые сверху списка |
| `model` | TEXT | id модели (`kimi-k3` / `MiniMax-M3`); NULL → default |
| `status` | TEXT | `'dialog'` (зарезервировано: extraction → review → build) |
| `extraction_json`, `model_spec_json` | TEXT | зарезервированы под срез №2 |
| `created_at` | REAL | |

Инварианты:
- **И-3.** Автотайтл ставится ровно один раз: `UPDATE … WHERE title='Новый диалог'`
  — переименование юзером автотайтлом не перекрывается. Формат: первые 48 символов
  первого сообщения, переносы → пробелы, обрезка с «…».
- **И-4.** `delete_chat`: сообщения стираются сразу, файлы **этого диалога**
  (`chat_id` совпал) уходят в корзину (`deleted_at`, TTL 7 дней), потом чат.
  Файлы без привязки (legacy, `chat_id IS NULL`) не трогаются.
  Привязка ставится при загрузке (форма `chat_id`) или при первом
  использовании в сообщении (`attach_file_to_chat` — только если NULL).
- **И-5.** Сортировка списка: `pinned DESC, COALESCE(last_at, created_at) DESC`,
  где `last_at` — `MAX(created_at)` по сообщениям. Пустой чат сортируется
  по дате создания.

### messages — сообщения

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | |
| `chat_id` | TEXT | |
| `role` | TEXT | `user` / `assistant` |
| `content` | TEXT | полный текст (для assistant — после завершения стрима) |
| `attachments_json` | TEXT | JSON-массив метаданных файлов, приложенных к сообщению |
| `created_at` | REAL | |

Индекс `idx_messages_chat(chat_id, created_at)` — покрывает оба чтения:
контекст для LLM (последние 20, DESC LIMIT + reverse) и полная история для
отрисовки (первые 200, ASC LIMIT).

- **И-6.** Сообщение юзера пишется в БД **до** вызова LLM, ответ ассистента —
  **после** завершения стрима. Обрыв стрима → ответ не сохранён (намеренно:
  недописанный ответ в контексте хуже, чем его отсутствие).

### files — загруженные файлы

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | имя файла на диске = этот id |
| `user_id` | TEXT | владелец; на диске `DATA_DIR/files/<user_id>/<id>` |
| `chat_id` | TEXT | диалог-владелец; NULL = legacy без привязки |
| `orig_name` | TEXT | оригинальное имя (только в БД, на диске нет) |
| `mime`, `size` | | |
| `path` | TEXT | путь к оригиналу |
| `parsed_path` | TEXT | путь к извлечённому тексту (.txt рядом) |
| `kimi_file_id` | TEXT | id в Kimi Files API (только при fallback на сканах) |
| `parse_status` | TEXT | `uploaded → processing → ready | error` |
| `deleted_at` | REAL | NULL = жив; NOT NULL = в корзине, с этой метки идёт TTL |
| `created_at` | REAL | |

Инварианты:
- **И-7.** Все чтения (`list_files`, `get_file`) фильтруют `deleted_at IS NULL` —
  корзина невидима для API, но занимает диск и квоту (осознанно: иначе корзина —
  способ обойти квоту).
- **И-8.** `get_parsed_text` читает текст с диска по `parsed_path`, а не хранит
  его в БД — БД не раздувается, тексты не дублируются.
- **И-9.** Один пользователь не может получить чужой файл: `get_file(fid, uid)`
  с `WHERE user_id` — чужой id = 404.

### usage_events — учёт токенов

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | |
| `user_id`, `chat_id` | TEXT | |
| `kind` | TEXT | `chat` сейчас; `extract` / `build` — под срезы №2–3 |
| `model` | TEXT | **какая модель реально ответила** (`kimi-k3`, `MiniMax-M3`, `mock`) |
| `prompt_tokens`, `completion_tokens`, `total_tokens` | INTEGER | |
| `created_at` | REAL | |

Индекс `idx_usage_user(user_id, created_at)` покрывает `usage_summary`
(totals, by_day за 30 дней, by_model).

- **И-10.** Запись пишется после успешного завершения стрима. Если usage от
  провайдера не пришёл — считается оценка (символы/4) и пишется как есть;
  флаг `estimated` в БД не сохраняется (точность учёта — см. docs/llm-providers.md).

### jobs / reports — зарезервированы

`jobs(id, chat_id, type, status, progress, result_json, error, created_at,
updated_at)` и `reports(id, chat_id, path, qa_json, kind, created_at)` созданы
в схеме, но кодом не пишутся — под срез «сборка Excel-модели» (прогресс-задачи
и артефакты с QA). Не удалять: миграции не умеют откатываться.

## 4. Политика миграций

Механика: `SCHEMA` (CREATE TABLE IF NOT EXISTS) + список `MIGRATIONS` вида
`(таблица, колонка, DDL)`, который делает `ALTER TABLE ADD COLUMN`, если колонки
нет в `PRAGMA table_info`.

Правила (логика каждого):

1. **Только additive.** Новые таблицы и новые колонки — да; переименование,
   удаление, смена типа — нет. Причина: нет механизма отката, а прод-БД одна.
   Нужна смена формата → новая колонка рядом + перенос чтения, старая
   остаётся мусором (как `kimi_file_id` после ухода на локальный парсинг).
2. **Новая колонка обязана быть nullable или иметь DEFAULT.** `ALTER TABLE ADD
   COLUMN` в SQLite не даёт добавить NOT NULL без дефолта на непустую таблицу.
3. **Миграция идемпотентна.** Запускается при каждом старте; проверка «колонка
   уже есть» — по `table_info`, а не по версии схемы. Поэтому записи в
   `MIGRATIONS` не удаляются никогда — только дополняются.
4. **Нет данных — нет миграции данных.** Если новая колонка требует пересчёта
   старых строк (backfill), backfill — отдельным пунктом в миграции с проверкой
   «уже посчитано», а не ручным SQL на проде.
5. **Сначала код, совместимый с обеими схемами, потом включение.** На время
   выката старый и новый код должны работать с любым состоянием БД (у нас
   rolling-пересоздание контейнера — окно в секунды, но правило дешёвое).

## 5. Retention и чистильщик

Фоновая задача `cleanup_loop` (запускается в lifespan приложения, интервал
`CLEANUP_INTERVAL_SEC` = 1 час, исключение внутри не убивает процесс):

| Что чистит | Условие | Действие |
|---|---|---|
| Корзина файлов | `deleted_at < now - 7 дней` (`TRASH_TTL_DAYS`) | стереть `path` и `parsed_path` с диска, удалить строку |
| Анонимные юзеры | `username IS NULL AND last_seen_at < now - 30 дней` (`ANON_TTL_DAYS`) | стереть файлы с диска, `delete_user_cascade`: files → usage_events → (messages, jobs по каждому чату) → chats → users |

- **И-11.** Каскад юзера — полный: после `delete_user_cascade` не остаётся
  ни строки, ни файла на диске.
- **И-12.** Сообщения и usage удалённых диалогов уходят вместе с ними;
  usage-события при удалении чата **не** чистятся (они про деньги, а не про
  контент — статистика юзера не должна меняться от удаления диалога).

## 6. Квота диска

`user_usage(uid)` — сумма `size` по всем файлам юзера, включая корзину (И-7).
Лимит — `quota_bytes` (200 МБ default). Проверка на upload в routes_files.
Квота мягкая: меняется прямым UPDATE по строке юзера, пересчёта занятого
места по диску нет — доверяем записи `size` из БД.

## 7. Что сюда ляжет в срезе №2 (прогноз)

- `chats.extraction_json` — результат Extraction Agent (JSON бизнес-допущений);
  `status`: `dialog → extracting → review → building → done`.
- `jobs` — задачи сборки модели с прогрессом для SSE.
- `reports` — сгенерированный xlsx + QA-отчёт (`qa_json`).
- Возможно, `usage_events.kind` начнёт писать `extract`/`build` — появится
  разрез стоимости по этапам. Миграций не нужно: колонки уже есть.
